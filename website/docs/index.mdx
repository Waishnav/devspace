Heavy AI users already run several coding agents. Codex plans well, Claude
implements carefully, another harness is good at driving a browser — and today
you are the one copying context between them and deciding what to prompt next.

DevSpace moves that routing into software. It gives any coding harness the
ability to **call other harnesses as bounded subagents** and to **program
multi-agent loops** as replayable scripts. The model you talk to becomes the
intent translator; DevSpace is the layer it uses to dispatch, wait on, and
combine work from the rest.

## Why agent-agnostic

Every provider is racing to make _their_ agent the orchestrator. In practice,
people already pick a different model and harness per task:

| Task | A typical pick today |
| --- | --- |
| Planning and review | Codex with a high-effort GPT model |
| Implementation | Claude Code with Sonnet or Opus |
| Exploration | a cheap, fast model through OpenCode or Pi |
| End-to-end QA | a harness with browser tools |

That matrix is personal, and it changes every few weeks. DevSpace keeps it as
configuration — [profiles](/orchestration/profiles) you own — instead of
locking it into one vendor's product. The orchestrating model only sees a
catalog of names and descriptions and chooses from it.

## Local-first

DevSpace runs on your machine, against your real checkouts, with your
installed CLIs and existing subscriptions. Nothing is uploaded to a DevSpace
service; there isn't one. MCP hosts reach it through a tunnel you own and a
password only you have.
